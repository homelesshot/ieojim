# 이어짐 — 위기가구 긴급복지 상담 도우미

녹음 한 번으로, 현장 상담을 **예비판단부터 상담일지 초안까지** 자동으로 이어주는 AI 솔루션. 현장에서 "기억에 의존해 사무실에서 다시 쓰던" 이중기록을 없애고, 상담원이 놓치던 공적 지원 연계를 돕습니다.

## 1. 팀 기본 정보

## 2. AI 솔루션

### 2.1 문제 정의
거리 아웃리치·쪽방 상담 등 **현장 사회복지사**는 대상자를 만난 자리에서 종이나 기억에 의존해 상황을 파악하고, **사무실로 돌아와 컴퓨터에 다시 입력**합니다. 이 이중기록 때문에:

- **상담 1건에 평균 약 22분** 소요 (내부 측정: 종이 3.2분 + 컴퓨터 재입력 12.0분 + 서류 6.8분) — **재입력 12분이 가장 큰 낭비 지점**
- 시간·전문성 부족으로 **공적 지원 연계율이 매우 낮음** (측정 기간 39건 중 1건, 약 3%)
- **신규·비전문 직원**은 1건 판단에 약 40분 — 긴급복지 기준이 복잡해 진입장벽이 큼
- 대상자들이 시설입소·병원·공공기관 연계를 두려워해 서비스 이용을 기피하는 경향까지 겹침

즉, **현장의 판단·기록·연계를 한 번에 돕는 도구**가 없다는 것이 핵심 문제입니다.

### 2.2 AI 솔루션 소개

#### 솔루션 개요
**이어짐**은 현장에서 휴대폰으로 상담 상황을 **녹음(또는 타이핑)** 하면, AI가 그 내용에서 긴급복지 판단에 필요한 항목(위기사유·거주·소득·재산·건강 등)을 **자동으로 추출·정리**하고, 단계별로 확실한 항목은 자동으로 넘어가며 불확실한 항목만 상담원에게 확인을 요청합니다. 끝까지 진행되면 **긴급복지 예비판단 → 지원 연계 안내 → 상담일지 초안(한글 .hwpx)** 까지 한 번에 만들어집니다. 상담원의 작업은 사실상 "녹음 버튼 한 번 + 확인"으로 줄어듭니다.

#### 설치 및 실행 방법
- **별도 설치 없음.** 최신 브라우저(모바일 크롬/사파리·삼성인터넷, PC 크롬/엣지)에서 링크만 열면 즉시 사용.
- 단일 HTML 파일로 동작하며, 음성 변환(STT)과 AI 항목 추출은 **Supabase Edge Function 프록시**를 통해 처리됩니다(실제 API 키는 서버에만 보관, 화면 코드에는 없음).
- 자체 배포 시: 정적 호스팅(GitHub Pages 등)에 HTML 업로드 + Supabase 프로젝트(Edge Function·DB) 연결. *실제 API 키·비밀번호는 이 문서와 저장소에 포함하지 않습니다.*

#### 주요 기능
- **녹음/타이핑 → AI 자동 항목 추출**: 상담 내용에서 11개 항목을 구조화 JSON으로 추출(문제: 이중기록·재입력 제거)
- **단계형 예비판단**: 위기사유→가구·거주→소득·재산→건강 순으로, 확실하면 자동 진행·불확실하면 확인 요청(문제: 판단 진입장벽·정확도)
- **긴급복지 예비판단 엔진**: 긴급복지지원법 기준(소득·재산·위기사유)으로 대상 가능성 판정 + 근거 제시
- **지원 연계 안내**: 공적 지원 항목 + 기관 자체 즉시지원 안내(문제: 낮은 연계율)
- **상담일지 초안 자동 생성·직접 편집(.hwpx)**: 관공서 제출 가능한 한글 문서로 바로 저장. 화면에서 직접 고친 내용도 "저장"을 누르면 .hwpx에 그대로 반영되고, 메모는 상담내용·상담의견·조치사항 3항목으로 자동 정리(문제: 서류 작성 시간)
- **모바일 우선 UI**: 한 화면에 한 단계씩, 이전/다음으로 진행(현장 사용성)
- **개인정보 보호 설계**: 실명·주민번호·주소는 문서에 저장하지 않고 `[___]`로 비움, 로그인·접근제어·암호화 저장

#### (선택) AI 성능 개선 시도
1. **음성 인식 한국어 고정** — gpt-4o 계열은 language 파라미터가 "힌트"로만 작동해 한국어 음성에 영어가 섞이는 문제가 있어, 디코더 단계에서 언어를 실제로 강제하는 **whisper-1로 교체**해 안정화.
2. **항목 자동추출 정확도 개선 — 단순 JSON 지시 → Structured Outputs(JSON Schema strict) 전환**
   - **문제**: "JSON으로만 답하라"는 프롬프트 지시만으로 뽑으니, 소득·재산 등 일부 필드가 통째로 누락되거나 형식이 흐트러지는 사고가 재현됨.
   - **원인**: 프롬프트 지시는 모델이 "따르길 기대"하는 수준이라 강제력이 없었음.
   - **조치**: Structured Outputs(`response_format: json_schema, strict:true`)로 전환 — 스키마를 요청에 함께 보내 필수 필드는 생략 불가, 불확실한 값은 추측 대신 반드시 `null`로 규정.
   - **효과**: 필드 누락은 이후 재현되지 않음. 다만 "채운 값이 맞는지"는 별개라, 가상 사례 반복 검증(4번)에서 값 정확도를 계속 검증·개선 중.
3. **대용량·특이 코덱 음성파일 STT 우회**
   - **문제**: 25MB 안팎 대용량 녹음이나 일부 m4a가 Whisper API에서 "Invalid file format"으로 거부되는 사고가 반복 신고됨.
   - **원인 조사**: Edge Function 로그로 실패한 실제 파일을 직접 대조(ffprobe 코덱 확인 등)해, 파일명·크기·코덱은 정상인데도 API가 거부하는 경우가 있음을 확인.
   - **조치**: 서버가 크기·형식 오류를 반환하면, 클라이언트가 Web Audio API로 오디오를 직접 디코딩해 18MB 이하 WAV로 재인코딩·분할 업로드 후 이어붙임 — "실패하면 다른 형식으로 우회 재전송"하는 방어적 설계.
4. **가상 인터뷰 케이스로 반복 자체 검증(QA) 루프** — 실제 대상자 정보 없이 AI로 만든 가상 상담 인터뷰(누적 71건, H/R/D/E/F/C/O/X 8개 유형)를 라이브 서비스의 실제 추출 로직(`requestExtractionV4`)으로 그대로 실행한 뒤, 사람이 원문과 한 건씩 대조해 "근거 없이 지어낸 값", "반대로 분류된 값(예: 받아야 할 돈을 빚으로 기재)", "위기사유 배열이 명백한 위기 상황인데도 비어 판정 자체가 뒤집히는 오류" 같은 패턴을 찾아 추출 프롬프트에 구체적 예시로 반영하는 과정을 여러 차례(1차 → 2차 → 3차) 반복. 프롬프트 보강만으로는 같은 유형의 오류가 일부 재발하기도 해서, "한 번 고쳤다"가 아니라 "매 차수 재검증"을 원칙으로 운영 — 상세 사례별 대조 결과는 저장소·프로젝트 문서로 축적.

### 2.3 이용자용 가이드
> 📗 **한눈에 보는 시각 가이드** — [**이어짐 이용 가이드 (스크린샷 · 3단계)**](https://homelesshot.github.io/ieojim/guide-user.html)

**이용 전 준비**: 스마트폰/PC 브라우저, 인터넷. 설치 불필요 — 다만 **상담을 저장하고 이어서 조회**하려면 회원가입이 필요합니다(로그인 없이도 판단·문서 생성 자체는 100% 동작).

**회원가입(선택, 상담 저장 시 필요)**:
1. 화면 좌상단 메뉴 버튼 → 사이드바에서 **로그인** 버튼을 누른다.
2. **로그인/회원가입** → 하단의 **회원가입**을 누른다.
3. 이름, 이메일, 비밀번호(확인 포함 2회 입력)로 가입한다.

**상담 진행 방법**:
1. 시작 방법은 3가지 — **[상황 없이 바로 입력]** · **[🎤 녹음 버튼]** · **[텍스트 입력창에 상담 내용 입력]** 중 상황에 맞게 고른다(다양하게 섞어 써도 됨).
2. 녹음·입력한 내용을 AI가 인식해 관련 항목을 **자동으로 선택**한다. 화면 상단의 **진행순서 표시(①~⑨)**를 보면서, 자동 선택되지 않은 항목은 상담원이 직접 채우며 **이전/다음**으로 단계를 넘긴다(이전으로 돌아가면 진행순서 표시도 함께 줄어든다).
3. 마지막 단계에서 **예비판단 실행** 버튼을 누르면 **① 예비판단 결과 → ② 지원 연계 안내 → ③ 상담일지 초안**이 순서대로 자동 생성된다.
4. 상담일지 초안을 **한글 문서(.hwpx)로 다운로드**해 내용을 확인·보완한다.
5. 화면 하단 또는 사이드바의 **[+ 새 상담 시작]**으로 다음 상담을 이어간다.

**참고 기능**:
- **가명화 도우미**: 녹음 직후 사이드바의 가명화 도우미를 누르면, 녹음 과정에서 인식된 이름·전화번호 등 개인정보를 상담원이 직접 확인하며 가명으로 바꿀 수 있다.
- **최근 상담 목록**: 로그인 상태라면 사이드바 **[최근]** 아래에 이전 상담 기록이 저장되어, 이어서 조회·수정할 수 있다.
- **설정**: 사이드바 설정 메뉴에서 언제든 **🤖 AI·개인정보 안내**, **🔒 개인정보 처리방침**, 암호화 키 등을 다시 확인할 수 있다.

**유의사항**:
- 이름은 **실명 대신 가명·이니셜**로 입력하세요. 실명·주민번호·주소는 문서에 담지 않습니다.
- 결과는 **예비판단(초안)** 이며, 최종 지원 여부는 담당 기관·지자체의 조사·결정에 따릅니다.
- 카카오톡으로 링크를 받아 열면(안드로이드), 상단 안내의 **"다른 브라우저로 열기"**를 눌러야 파일이 저장됩니다.
- 최신 업데이트가 바로 반영되도록, 사용 전에는 항상 브라우저를 **새로고침**해 주세요.

### 2.4 관리자용 가이드
> 📘 **한눈에 보는 관리자 가이드** — [**이어짐 관리자 가이드 (구조 · 운영 · 점검)**](https://homelesshot.github.io/ieojim/guide-admin.html)

**작동 구조**: 단일 HTML(프론트) + Supabase(백엔드).
- 화면(HTML)에서 녹음/입력 → **Supabase Edge Function**(`stt-transcribe`, `ai-draft` 등)이 OpenAI를 호출(실제 키는 서버에만 보관) → 결과를 화면에서 판정엔진에 태워 상담일지 생성.
- 로그인·상담 저장은 **Supabase Auth + Postgres**. 비로그인 상태에서도 판단·문서 생성은 100% 동작(저장·이어하기만 로그인 시 활성).

**사용 기술·외부 서비스**: HTML/JS(무프레임워크), Supabase(Auth·Postgres·Edge Functions·서울 리전), OpenAI API, GitHub Pages(정적 호스팅).

**개발 과정(요약)**: 챗봇형 UI → 실제 판정엔진 통합 → 로그인·상담 저장 → 사유서/상담일지 hwpx 양식 확정 → 단계형(페이지 넘김) UI → 녹음 STT → **AI 자동 항목 추출 원샷(v4)** → 대규모 가상 QA·프롬프트 보강, 모바일 로그인·거주지역 자동추정 등 현장 버그 수정, 상담일지 직접수정 hwpx 반영, 로그인 없이도 개인정보·AI 안내 열람, 대용량·특이 코덱 음성파일 STT 우회. 상세 개발 과정은 저장소의 `이어짐_발표대본_개발과정.md` 참고.

**운영 전 준비**: Supabase 프로젝트(서울 리전) + Edge Function에 OpenAI 키 설정(대시보드 Secrets), RLS 활성화. *키는 반드시 서버 환경변수로만 보관하고 저장소에 넣지 않습니다.*
**운영 중 유의**: 개인정보는 가명 입력 원칙, 민감 스냅샷은 암호화 저장(pgcrypto), 상담원별 접근은 RLS로 본인 것만.

**적용 개요**: 거리 아웃리치 담당 사회복지사가 실제 현장 상담에 이어짐을 사용(비로그인 모바일). 도입 전 현재 업무를 **baseline으로 측정**한 뒤, 도입 후 같은 지표를 재측정해 비교. 외부 기관에는 `feedback.html` 피드백 폼을 통해 별도로 실사용 응답을 수집하고 있습니다.

> ⚠️ *baseline(39건 평균)과 같은 방식의 다건 평균은 아직 못 냈고, 지금까지 들어온 개별 사례 2건 기준입니다. 더 모이는 대로 갱신합니다.*
> - 상담 1건 처리시간: 사례 A **약 60분 → 약 1분**(자기보고), 사례 B **약 40분 → 약 20분** — 두 사례 모두 단축.
> - 공적 연계율: 아직 측정 안 됨 *(수집 중 — 케이스 기록 시트에 건수가 더 쌓여야 baseline과 비교 가능한 비율 산출 가능)*
> - 업무 부담 체감: 사례 A "훨씬 줄었다", 사례 B "감소" *(5점 척도 응답: 각 5/5, 3/5 — 표본 2건이라 baseline의 4/5와 직접 비교하기는 아직 이릅니다)*

**타분야 확산 참고 2건(핵심 도메인 밖 ― 타지역·타분야)**:
- **(노인복지시설, 사회복지사)**: 상담 1건 소요 **약 27분 → 약 5분**, 만족도 4/5, 계속 사용 "예"(*"모니터지 작성 시간 단축"*). AI 추출 정확도 **2/5**. 개선 요청: *"상황이나 문제점에 있어 본인 중심만 입력 가능(보통 가족 문제와 연계하여 욕구 발생)"* — 가족 문제 연계 항목이 없어 정확도가 낮게 나온 것으로 파악.
- **(기타 유형·복지 유관기관)**: 상담 1건 소요 **약 10분 → 약 5분**, 만족도 4/5, 업무 부담 감소(5→3), AI 추출 정확도 **5/5**, 의향 "조건부". 도움된 점: *"대상자를 분류하는 데 도움"*. 개선 요청: *"좀 더 세부적인 선택지가 필요"*, 무엇이 개선되면 좋을지는 *"아직 잘 모름"*으로 응답 — 구체적 요구가 아직 명확하지 않아 다음 응답에서 더 파악할 예정.
- ※ 이어짐은 **긴급복지 위기가구**에 맞춰 튜닝돼 있어, 노인복지 사례관리(가족 문제 연계 등) 맥락에선 추출 정확도가 낮게 나옵니다 — 결함이 아니라 **핵심 도메인 집중의 방증**입니다. 요청받은 "가족 문제 항목"은 **주제(긴급복지 위기가구)를 유지하기 위해 본선 제품에는 넣지 않고 3.3 확산 과제로 이관**합니다.
- 의미: **같은 문제(현장 상담 이중기록·서류 시간)**를 가진 다른 분야·타지역 기관 2곳 모두에서 처리시간이 절반 이하로 줄었음 → 심사기준 ④임팩트(비슷한 문제를 가진 다른 기관의 참고·적용 가능성)의 실증.

⚠️ *모두 소규모 표본·자기보고 값이며, 도입 후 정량 데이터는 feedback.html로 계속 수집 중입니다.*

**참고 — 기능 검증(가상 사례, 실사용 아님)**: 실제 대상자 없이 AI로 만든 가상 인터뷰 사례를 실제 서비스 로직에 그대로 태워, 사람이 원문과 대조해 오류를 찾는 자체 QA. *현장 실사용 데이터와는 구분되며, ①완성도(다양한 상황 처리 능력) 근거로만 씁니다.*
- **총 71건**(1·2차 41건 + 3차 신규 30건, 8개 위기유형 H/R/D/E/F/C/O/X 고르게 포함)을 **3차에 걸쳐** 검증. **2차 검증(41건) 기준 AI 자동화율 약 75%, 항목 정확도 약 83%**, 개인정보 가명화 정상.
- **3차 검증(신규 30건, 2026-09-16)**에서 가장 심각한 **새 오류 유형**을 발견: **위기사유(crisis) 배열이 명백한 위기 상황(노숙·경매로 인한 퇴거 위기 등)에도 빈 채로 남아, 판정 자체가 "위기사유 미해당"으로 뒤집히는 사고**(최소 2건 확정, 판단 여지가 있는 경계 사례 추가 확인). 그 외 체불임금을 빚(debt)으로 반대 분류, 보증금(deposit) 필드에 다른 금액을 잘못 채우는 등 재발·신규 오류를 함께 발견해 **추출 프롬프트를 즉시 보강**했습니다(앱 내 버전기록 `v4-track a98`).
- 발견한 오류 패턴마다 **AI 추출 프롬프트를 매 차수 보강**했고, 재발·신규 오류를 모두 기록해 다음 차수에도 재검증합니다(상세 오류 패턴·검증 이력은 앱 내 버전기록(VERSION_LOG `a73`·`a84`·`a98`)과 저장소 `이어짐_검증기록_템플릿.md` 참고). 3차 보강분(a98)을 반영한 재검증 결과는 다음 차수에서 갱신합니다.

### 3.2 시행착오와 개선
- **녹음 중 화면 꺼짐 사고**: 화면이 꺼지면 마이크가 끊겨 뒷부분이 무음·환각("시청해주셔서 감사합니다" 반복)으로 채워지고 다음 버튼이 안 눌리던 현장 사고 → **화면 꺼짐 방지(Wake Lock)** + 꺼지면 즉시 녹음 중단·자동 진행으로 개선.
- **STT 언어 혼입**: 한국어 음성에 영어가 섞임 → 모델을 whisper-1로 교체해 한국어 고정.
- **모바일 한 화면 초과**: 항목이 많은 단계가 스크롤을 유발 → 한 단계를 두 화면으로 분할해 스크롤 제거(코치 피드백 반영).
- **카카오톡 저장 불가**: 안드로이드 카톡 인앱브라우저에서 파일 저장이 안 됨 → "다른 브라우저로 열기" 원탭 안내 추가.
- **보안 설계 딜레마(가장 크게 고민한 지점)**: 상담원 개인 비밀키(제로지식) 암호화를 넣었으나, 조직의 법적 접근 의무·데이터 유실 위험과 충돌 → **조직도 접근 가능한 방식(RLS+서버키 암호화)**으로 결정.
- **재녹음/중지 버그(6단계 디버깅 사례)**: 재녹음 시 버튼 먹통·마이크 계속 켜짐이 여러 차례 신고됨.
  - 세대 번호 경쟁 상태(a57) → 오류 메시지 오분류(a58) → 화면 갱신 실패 시 마이크 방치(a59) → 녹음 중 다음버튼 차단(a60)까지 고쳤으나 현장에서 계속 재현.
  - 원격 iOS 콘솔을 볼 수 없어(윈도우 환경) `?debug=1`로 열리는 임시 콘솔(eruda)을 넣어 실제 오류를 확보 → **진짜 원인**: 마이크 버튼(#micBtn)이 최초 "환영 화면"에만 있어 재녹음부터는 null인데, null 체크 없이 접근해 녹음 종료 처리가 중간에 멈춤.
  - null 가드로 근본 해결, 재테스트 확인 후 디버그 도구 제거(a57~a63). *"추정으로 고치다 안 되면 진단 도구부터 붙여 실제 증거를 확보한다"*는 과정 자체가 남을 사례.
- **음성파일(STT) "Invalid file format" 오류 — 로그 대조로 추정을 검증하며 좁힌 사례**: 특정 m4a 녹음(13분 안팎)이 서버에서 "Invalid file format"으로 거부되는 신고가 반복됨. 파일명 인코딩(비ASCII 파일명) 문제로 처음 추정해 안전한 파일명으로 바꿔봤지만 재현 지속 → Supabase Edge Function 로그를 직접 대조해 파일 크기(25MB 제한 근접) 가능성으로 좁히고 서버에 크기 가드·상세 로그를 추가 → 그래도 24MB 미만의 정상 크기 파일이 계속 거부되는 사례가 로그로 재확인되어, ffprobe로 실제 파일을 직접 분석한 결과 코덱 자체는 지극히 표준적(aac-lc)이라 "파일 문제"가 아니라 "이 특정 파일에 대한 OpenAI API 쪽의 처리 이슈"에 가깝다는 결론에 도달. 원인을 원천적으로 고칠 수 없으니, **실패 시 브라우저에서 직접 WAV로 재인코딩해 분할 재전송**하는 우회 로직으로 방향을 바꿔 반영. 이 과정에서 "이미 반영되어 있다"고 잘못 기록되었던 이전 인수인계 내용을 실제 코드와 로그로 재확인해 바로잡고 그제서야 실제로 반영한 사례이기도 함 — 추정을 실제 증거(로그·코덱 분석)로 검증하는 습관의 중요성을 다시 확인.
- **한글(.hwpx) "저장 후 다운로드" 안 열림 — 6차례 구조 추정 실패 끝에 결정적 대조 테스트로 해결**: 상담일지 초안을 화면에서 고친 뒤 "저장"을 누르고 받은 .hwpx 파일이 한글 프로그램에서 "손상되었거나 변조되었을 가능성"으로 열리지 않는 신고가 반복됨. XML 제어문자 제거·문단 캐시(linesegarray) 보강·스타일 참조 타입 수정·문단 생성 방식 전환 등 다섯 차례에 걸쳐 구조를 추정해 고쳤지만 매번 재현 — 한글 프로그램이 없는 환경에서 zip·XML 유효성만으로는 실제 렌더링 성공을 보장할 수 없다는 한계에 부딪힘. 결국 "① 바로 다운로드(항상 열림) ② 저장만 누름(수정 없음) ③ 수정 후 저장" 3개 파일을 동일 상담으로 정확히 대조하는 결정적 테스트를 통해, 실제 차이가 "저장 경로가 표 칸을 전부 하드코딩된 값으로 비운 것"과 "메모를 검증되지 않은 방식으로 한 줄로 이어붙인 것" 두 가지뿐임을 특정 — 이미 실제 운영에서 검증된 값·방식을 저장 경로에도 그대로 재사용하도록 수정. 여전히 실제 한글 프로그램으로 최종 렌더링 확인은 못 했다는 한계는 남아 있지만, "구조를 추정해서 고치기"의 한계에 부딪혔을 때 "실제 대조 데이터를 받아 좁히기"로 접근을 바꾼 사례.
- **현장 피드백 반영(2차 실사용)**: 팀장·관리자 피드백 중 **핵심 도메인 안의 것**(가정폭력 피해/가해 구분·시작단계 필수확인 안내·결과 화면에서 대상유형 직접 수정→상담일지·hwpx 반영)은 **v4-track a69·a70·a81로 반영**. 반면 **① 타분야(노인복지) 기관의 "가족 문제 항목" 요청**과 **② 목적별 상담일지 양식 선택(외부발송/보관용) 요청**은, 피드백을 무조건 반영하기보다 판단 기준을 세워 **본선 제품에는 넣지 않는** 결정을 내렸습니다 — ①은 **처음 정의한 문제(긴급복지 위기가구)와의 정합성**을 위해, ②는 **기관별 양식으로 넓히는 확장성 과제**라서 각각 **확산 과제(3.3)로 이관**. "무엇을 넣지 않을지"를 문제 정의·범위 기준으로 판단한 사례입니다.
- **거주지역·연령·성별 자동추정 오판 제거**: 초기에는 원문에 근거가 없으면 지역을 기본값(대도시)으로 자동 채워, 예컨대 인천 사례가 서울로 표기되는 등 오판이 생겼음 → **선택하지 않으면 공란**으로 두고 상담원이 직접 고르게 바꿔(현재는 시범기관 소재지 인천 기준) 근거 없는 자동판정을 없앰.
- **상담일지 "직접 수정"이 최종 한글 문서까지 반영**: 결과 화면에서 상담원이 고친 내용이 복사·txt에만 반영되고 한글(.hwpx)에는 빠지던 정보 불일치를 해소 — ⑦ 화면에 "저장" 버튼을 두어 **화면에서 고친 그대로 .hwpx에 반영**되게 함. 메모도 "상담내용·상담의견·조치사항" 3항목으로 자동 정리.
- **모바일 로그인·시작 안내 정비**: 휴대폰에서 로그인이 안 되던 문제(비밀번호 자동 대문자화 등) 수정, 처음 쓰는 사람이 로그인을 지나치지 않도록 좌상단 메뉴 안내, 로그인 없이도 AI·개인정보 안내를 첫 화면에서 볼 수 있게 개선.
- **AI 추출 정확도 자체 QA(가상 누적 71건)**: 실제 대상자 없이 만든 가상 사례를 3차에 걸쳐 실제 로직으로 검증·프롬프트 보강(3.1 참고). 3차(신규 30건)에서 **위기사유 배열이 비어 판정이 뒤집히는 최고 심각도 오류**를 새로 발견해 즉시 보강(`a98`) — 100% 근절은 못 했고 재발·신규 오류를 기록해 계속 재검증 중.
- **남은 한계**: 도입 후 정량 데이터가 아직 축적 중, hwpx 저장 경로의 실기기 최종 확인 필요, STT 우회 로직도 저전력 모바일 기기에서의 안정성 재확인 필요, AI 추출 프롬프트는 실사용하며 계속 조정 중, 여러 상담원 응답을 모아 보는 관리자 검수 화면은 다음 단계 과제.

### 3.3 향후 계획 및 임팩트 확산
- **오픈소스 공개 지향** — 예산이 부족한 사회복지 기관도 장벽 없이 도입할 수 있도록.
- **법인 내부에 확산 기반이 이미 실재**: 이어짐은 노숙인 아웃리치에서 출발했지만, 운영 법인(인천내일을여는집)은 **가족상담소(가정폭력 가해/피해 상담)·내일여성쉼터·부천 여성의 쉼터(가정폭력 피해자 보호)·시니어클럽·푸드마켓·푸드뱅크·해인지역아동센터**에 더해 **무료급식소(독거노인·차상위 어르신)·외국인 취약계층 긴급지원**까지 산하에 두고 있습니다. 이들 자매기관 상당수는 **똑같이 "현장 초기상담 → 사무실 재입력" 이중기록 문제**를 겪으며, 가정폭력 피해자·외국인 긴급지원처럼 **긴급복지 위기가구 성격이 그대로 겹치는** 대상도 많습니다. 즉 별도 영업 없이 **법인 안에서 바로 확산할 수 있는 실질 경로가 이미 있고**(대상유형·지역 기준을 각 기관에 맞게 조정), 이것이 타분야 실증과 함께 확산 가능성의 근거가 됩니다.
- **확산 실증(초기)**: 노인복지시설(타지역·타분야)이 상담 기록 시간을 **27분→5분**으로, 기타 유형 복지 유관기관(타분야)이 **10분→5분**으로 줄임 — "비슷한 문제(현장 상담 이중기록·서류)"를 가진 다른 기관에도 통한다는 증거가 2건으로 늘었습니다.
- **주제 유지 원칙**: 본선까지는 **핵심 주제(긴급복지 위기가구 현장 상담·판단·서류화)를 유지**합니다. 노인복지의 "가족 문제 항목"이나 목적별 서류 양식 선택처럼 **다른 분야·기관 전용 기능**은, 본선 이후 **대상유형·판정기준·추출 프롬프트·서류 양식을 그 분야에 맞게 확장하는 별도 과제**로 둡니다(예선 문제 정의와의 일관성 유지 — 심사기준 ③ "처음 해결하려던 문제" 기준에 맞춤).
- **운영 계획**: 상담원 계정·접근권한·보관기간 정비, 실사용 데이터로 판정·추출 정확도 지속 개선, 외부 기관 피드백 폼 응답을 지속 수집해 확산 과제 우선순위에 반영.

아래 개인정보·AI 윤리 5개 항목에 대한 답변을 작성해 주세요.

1) 어떤 개인정보를 모으고, 어디에 쓰고, 어디로 보내는지 설명해 주세요. (예: 이름·연락처·이용 기록 등 수집 항목, AI 모델·외부 API로 전송하는 경우 포함)

   상담 내용(음성/텍스트)에서 위기사유·거주지·가구원수·소득/재산·건강상태 등 긴급복지 예비판단에 필요한 항목을 다룹니다. 녹음 파일은 서버(Supabase Edge Function)를 거쳐 OpenAI Whisper(STT)로 **전송만** 되고 서버에 저장되지 않으며, 변환된 텍스트는 OpenAI(gpt-4o 계열)로 전송해 항목 추출·상담일지 문장 다듬기에 사용합니다. 로그인 시에만 이메일·표시 이름·소속 기관을 Supabase Auth·DB에 저장하며, **로그인 없이도 판단·상담일지 생성 기능은 100% 동일하게 동작**합니다(저장·이어하기만 로그인 필요). 대상자 이름은 가명·이니셜 입력을 원칙으로 안내하고, 그럼에도 이메일·주민번호·카드번호·전화번호처럼 형식이 뚜렷한 개인식별정보 4종은 서버 전송 전 브라우저 안에서 자동으로 제거되며, 이름·지명 등 자유 형식 정보는 상담원이 "가명화 도우미"에서 직접 가릴 수 있습니다. 다만 음성 녹음 자체는 텍스트로 변환되기 전에 전송되므로 위 자동 마스킹이 적용되지 않는 사각지대가 있습니다 — 이를 정직하게 인지하고, 녹음 화면에 "대상자의 실명·주민번호·주소·연락처는 말로 하지 마세요(이름은 '어르신'·'A씨'로)"라는 안내를 눈에 띄게 띄워 현장에서 먼저 줄이고 있으며, 국내·온디바이스 STT 도입을 다음 단계 과제로 두고 있습니다. 저장이 필요한 경우(로그인 시 이어하기)에도 상담 스냅샷은 서버키로 암호화(pgcrypto)해 보관하고, RLS(행 수준 보안)로 본인 상담원만 열람할 수 있게 접근을 제한합니다.

2) 개인정보를 수집·활용했다면, 이용자의 동의를 받았는지 또는 동의 없이 써도 되는 근거가 무엇인지 설명해 주세요. (예: 회원가입 시 동의 받음/ 별도 동의 없이 공개된 정보만 사용함 등)

   별도의 동의 체크박스는 받지 않습니다. 개인정보 보호법 제26조(업무위탁에 따른 개인정보의 처리 제한)·제28조의8(개인정보의 국외 이전)에 따라, 계약 이행을 위한 처리위탁(국외 이전 포함)은 위탁 사실·이전받는 자·목적·항목·보유기간 등을 개인정보 처리방침에 미리 공개하면 별도 동의 없이도 처리할 수 있다는 근거[^privacy-law]에 따라 구현했습니다. 서비스 화면에는 "🔒 개인정보 처리방침" 버튼이 항상 노출되고 최초 1회는 자동으로 안내가 뜨며, 대상자 본인에게는 상담원이 상담 시작 전 구두로 녹음·AI 처리 사실을 안내하도록 처리방침에 안내 문구를 포함했습니다. 국외 이전(OpenAI) 쪽 보유기간은 처리방침에 "악용 방지 모니터링 목적으로 최대 30일간 보관 후 삭제"로 명시돼 있습니다.
   *(사실관계 — 아직 채워야 할 부분: 국내 저장(Supabase, 로그인 시 상담 저장분)의 보유기간은 현재 처리방침에 "기관 내부 방침에 따름"이라고만 되어 있고 구체적인 기간·자동 파기 규칙은 아직 정해지지 않았습니다 — 기관 내부 논의로 확정 후 반영 필요.)*

3) 개인정보를 어떻게 처리하는지, 그리고 AI를 사용한다는 사실을 이용자에게 어떻게 알리는지 설명해 주세요. (예: 서비스 화면에 "AI가 생성한 답변입니다" 표시, 개인정보처리방침 페이지 등)

   위 2)의 개인정보 처리방침(국외이전 안내 포함)을 서비스 내 상시 접근 가능하게 배치했습니다. 화면 자체도 "AI 인식 결과 확인", "AI 초안 만들기"처럼 **AI가 처리한 단계임을 화면 이름 그대로 드러내는 구조**로 설계했습니다 — 녹음 직후 사람이 변환된 텍스트를 직접 확인해야만 다음 단계(AI 항목 추출)로 넘어가고, AI 인식이 끝나면 무엇을 인식했고 무엇을 못 했는지 별도 확인 화면에서 보여줍니다. 예비판단 결과 화면 최상단에는 "⚠ 이 판단은 예비판단이며, 최종 지원 여부는 담당 기관의 공식 심사를 따릅니다"라는 문구를 항상 표시합니다.

4) AI가 틀리거나 부적절한 답을 했을 때, 사람이 확인하고 고칠 수 있는 절차가 있는지 설명해 주세요. (예: 관리자 검수 화면, 신고 기능, 응답 로그 모니터링 등)

   소득·재산 등 예비판단 자격을 좌우하는 법적 핵심 항목 4개는 AI가 전부 자동으로 채워도 절대 자동으로 다음 단계로 넘어가지 않고, 상담원이 화면을 직접 보고 확인 버튼을 눌러야만 진행되도록 강제했습니다. 위기사유·거주지·건강상태 등도 AI가 불확실하다고 판단한 항목이 하나라도 있으면 그 화면에서 멈추고 사람이 직접 입력·확인하게 되어 있어, 전체 항목이 AI 판단만으로 자동 확정되는 경로가 없습니다. AI가 정리한 상담일지 초안 문장도 상담원이 화면에서 자유롭게 고쳐 쓸 수 있고, 고친 내용은 "저장"을 누르면 최종 한글(.hwpx) 문서에도 그대로 반영되며, 다운로드 전 항상 사람이 열람·수정합니다. (한계) 여러 상담원의 AI 응답을 모아 보는 별도 관리자 검수 화면이나 신고 기능은 아직 없고, 현재는 담당 상담원 본인이 매 건 직접 확인하는 구조입니다 — 다음 단계 과제로 남겨두었습니다.

5) AI 사용으로 이용자가 실제로 피해를 볼 수 있는 상황을 어떻게 막고 있는지 설명해 주세요. (예: 잘못된 의료·법률 정보 제공 방지, 생성형AI서비스 학습데이터로 사용되지 않도록 설정 등)

   AI가 의료·법률적 확정 판단을 하지 않도록 "예비판단"이라는 표현과 면책 문구를 결과 화면에 항상 노출합니다(실제 지원 여부는 담당 공무원·기관의 별도 심사). 음성 인식 환각(할루시네이션) 방지를 위해, Whisper가 무음·저신뢰 구간에서 "시청해주셔서 감사합니다" 같은 엉뚱한 문장을 만들어내는 사고가 실제로 있었고 이를 정규식 패턴과 신뢰도 점수(no_speech_prob, avg_logprob) 기준으로 걸러내는 안전장치를 서버에 적용했습니다. 소득·재산 값을 AI가 근거 없이 "0원"으로 지어내는 문제에도, 원문에 "없다/없음" 같은 명시적 표현이 없는데 4개 항목이 전부 0으로 나오면 지어낸 값으로 보고 미확인 상태로 되돌리는 로직을 추가했습니다. OpenAI API로 전송하는 데이터는 OpenAI의 API 데이터 사용 정책상 기본적으로 모델 재학습에 사용되지 않습니다(별도 옵트인 없이는 API 호출 데이터를 학습에 쓰지 않는다는 것이 OpenAI의 공개 정책입니다[^openai-policy]). 아울러 STT·AI 기능 호출에 로그인 여부와 무관하게 횟수 제한이 없어 키가 유출되면 무제한 호출이 가능한 상태임을 자체 점검(적대적 리뷰, 2026-09-09)으로 발견했고, 로그인 세션 토큰 우선 사용과 시간당 호출 횟수 제한(Edge Function + 카운터 테이블)을 모두 적용·배포 완료했습니다(2026-09-11) — 실제로 한도를 초과하면 호출이 차단되는 것을 서버 응답(HTTP 429, RATE_LIMIT)으로 확인했습니다. 또한 사용자·상담 텍스트가 화면에 표시되는 경로 전반에 대해 XSS(교차 사이트 스크립팅) 취약점 감사를 직접 수행해 악용 가능한 스크립트 주입 경로가 없음을 확인했고, 입력값 이스케이프를 한 단계 더 강화하는 심층 방어까지 적용했습니다. 이처럼 완성된 상태를 주장하기보다, 팀이 스스로 공격자 관점에서 점검(적대적 리뷰·보안 감사)하고 발견한 항목을 해결했거나 로드맵으로 공개하는 과정 자체를 안전성의 근거로 두고 있습니다.
